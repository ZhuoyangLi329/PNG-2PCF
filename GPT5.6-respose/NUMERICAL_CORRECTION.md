# 重分箱计数表的复现口径与更正

本文件更正 `REVIEW_zh.md` 第 5 节计数表中的两个例子；核心结论与 `[0.037,0.039)` 的 1262→1094 结果不变。复现应严格按原源码先计算 `kf=2*np.pi/L`，再计算 `dk=0.1*kf`。

在本次 NumPy 2.3.5 / SciPy 1.17.0 环境中，两种代数等价的写法相差一个浮点舍入单位：

```python
kf = 2*np.pi/2000.
dk = .1*kf                 # 0.00031415926535897936，原源码计算顺序
# .1*2*np.pi/2000.          # 0.0003141592653589793，不应用来声称逐步复现原源码
```

聚合索引使用 `(k/dk).astype(int)`。部分模式恰好落在聚合边界附近，所以这个微小差别会改变聚合组的成员及其 k_eff，随后影响窄 P bin 的归属。原源码顺序下应使用：

| P 区间 h/Mpc | 精确模式数 | 按聚合中心归类 | 相对计数差 |
|---|---:|---:|---:|
| [0.017,0.019) | 234 | **234** | **0%** |
| [0.037,0.039) | 1262 | 1094 | -13.3122% |
| [0.061,0.063) | 2994 | **2754** | **-8.0160%** |
| [0.085,0.087) | 6000 | 5352 | -10.8000% |

报告第 5 节中的 234→258、2994→3402 来自另一计算顺序，不应作为原源码顺序的确定计数。`local_test_results.json` 已记录上述原源码顺序的完整计数；执行时请用它与实际 cache 交叉核对，不要用报告旧行覆盖 JSON。

这还说明：把光滑积分的径向压缩缓存用于另一组不连续的 top-hat P-bin 选择，本身是一个不稳健操作。**修复不应仅是加浮点 epsilon 或更改截断规则，而应先按真实模式和测量 P-bin 边界选择，再在 bin 内聚合。** PP 与 XP 的求和必须使用和测量相同的 mode set。此处仍只证明计数/算子问题，没有测得它造成的 b1 或 sigma_s 参数偏移。
